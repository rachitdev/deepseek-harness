# Chapter 28: Coding Agents

## Core Idea
Move past raw generation ("vibe coding" for ideation) to a **human-led team of specialized coding agents**: the developer is the architect and orchestrator, the agents are force multipliers handling testing, documentation, review, and refactoring.

## Frameworks Introduced
- **Vibe coding as a starting point** — using LLMs for initial drafts, outlining complex logic, and quick prototypes. Its strength is overcoming the **blank-page problem** and accelerating discovery and ideation: transitioning from vague concept to tangible runnable code, exploring unfamiliar APIs, testing novel architectural patterns. The generated code is a **creative catalyst** to critique, refactor, and expand — not a deliverable. Robust, scalable, maintainable software demands the structured approach that follows.
- **The three foundational principles of the human-agent team**:
  1. **Human-Led Orchestration** — the developer is team lead and project architect, always in the loop: orchestrating workflow, setting high-level goals, making final decisions. The developer directs which agent to engage, provides context, and exercises **final judgment on any agent-generated output**.
  2. **The Primacy of Context** — "A powerful LLM with poor context is useless." Automated, black-box context retrieval is **avoided**; the developer assembles the briefing: **the complete codebase** (so the agent understands existing patterns and logic), **external knowledge** (documentation, API definitions, design documents), and **the human brief** (clear goals, requirements, PR descriptions, style guides).
  3. **Direct Model Access** — agents must be powered by direct access to frontier models. Less powerful models, or intermediary platforms that obscure or truncate context, degrade performance. The aim is the purest possible dialogue between the human lead and the model's raw capabilities.
- **The specialist agent team** — conceptual personas invoked within the LLM through role-specific prompts and contexts, not separate applications:
  - **The Orchestrator (the human developer)** — team lead, architect, final decision-maker; defines tasks, prepares context, validates all work.
  - **The Context Staging Area** — a dedicated per-task workspace, implemented as a temporary directory (`task-context/`) containing markdown files for goals, code files, and relevant docs.
  - **The Scaffolder Agent (the Implementer)** — writes new code, implements features, creates boilerplate from detailed specifications.
  - **The Test Engineer Agent (the Quality Guard)** — comprehensive unit, integration, and end-to-end tests.
  - **The Documenter Agent (the Scribe)** — clear, concise documentation for functions, classes, APIs, or entire codebases.
  - **The Optimizer Agent (the Refactoring Partner)** — proposes performance optimizations and refactoring for readability, maintainability, efficiency.
  - **The Process Agent (the Code Supervisor)** — a **two-stage critique-then-reflect** review: first identify potential bugs, style violations, and logical flaws like a static analysis tool; then **analyze its own critique** — synthesize findings, prioritize the most critical issues, **dismiss pedantic or low-impact suggestions**, and produce a high-level actionable summary.
- **The four principles for leading the augmented team**:
  - **Maintain Architectural Ownership** — you define the "what" and the "why"; the agent team accelerates the "how". You are the final arbiter of design.
  - **Master the Art of the Brief** — output quality directly reflects input quality. Think of the prompt not as a command but as a **complete briefing package for a new, highly capable team member**.
  - **Act as the Ultimate Quality Gate** — an agent's output is always a **proposal, never a command**. Treat the Reviewer Agent's feedback as a powerful signal, but validate, challenge, and approve with your own domain expertise.
  - **Engage in Iterative Dialogue** — if the initial output is imperfect, refine rather than discard. The Reviewer Agent's "Reflection" output is designed to **start a collaborative discussion, not be a final report**.

## Key Concepts
- **Industry context**: in early 2025 Alphabet CEO Sundar Pichai noted that at Google "over 30% of new code is now assisted or generated by our Gemini models, fundamentally changing our development velocity." Microsoft made a similar claim.
- **The frontier is empowerment, not replacement**: humans guide architectural vision and creative problem-solving; agents handle specialized scalable tasks.
- **Critique-and-reflection**: the second pass is what turns a wall of lint into a prioritized, actionable summary.
- **Prompts as code**: a version-controlled `/prompts` directory lets the whole team collaborate on, refine, and version agent instructions.

## Mental Models
- **You are hiring, not automating.** Every principle follows from treating the agent as a capable new team member who needs a proper briefing and whose work you review.
- **Context is the product you produce.** The Context Staging Area exists because assembling the right briefing *is* the developer's main work in this model.
- **Two-stage review beats one.** Critique finds everything; reflection decides what matters. A review that surfaces 40 items equally is not a review.
- **Dual-provider by default.** Two frontier models hedge against single-platform limitations and enable comparative analysis.

## Anti-patterns
- **Shipping vibe-coded output**: excellent for ideation, insufficient for robust, scalable, maintainable software.
- **Automated black-box context retrieval**: you lose control over what the model actually sees.
- **Routing through intermediary platforms that truncate context**: degrades performance below the model's real capability.
- **Ad-hoc context scripts**: use a configuration file so context assembly is transparent and repeatable.
- **Treating agent output as a command**: it is always a proposal.
- **Discarding imperfect output**: refine through iterative dialogue instead.
- **Unversioned prompts**: they are instructions to your team; treat them as code.

## Code Examples
The specialist agents' invocation prompts:
```
# The Scaffolder Agent — the Implementer
"You are a senior software engineer. Based on the requirements in 01_BRIEF.md and the
existing patterns in 02_CODE/, implement the feature..."

# The Test Engineer Agent — the Quality Guard
"You are a quality assurance engineer. For the code provided in 02_CODE/, write a full
suite of unit tests using [Testing Framework, e.g., pytest]. Cover all edge cases and
adhere to the project's testing philosophy."

# The Documenter Agent — the Scribe
"You are a technical writer. Generate markdown documentation for the API endpoints
defined in the provided code. Include request/response examples and explain each parameter."

# The Optimizer Agent — the Refactoring Partner
"Analyze the provided code for performance bottlenecks or areas that could be refactored
for clarity. Propose specific changes with explanations for why they are an improvement."

# The Process Agent — the Code Supervisor (critique then reflect)
"You are a principal engineer conducting a code review. First, perform a detailed critique
of the changes. Second, reflect on your critique to provide a concise, prioritized summary
of the most important feedback."
```

Context Staging Area layout:
```
task-context/
  01_BRIEF.md        # goals, requirements, PR description, style guide
  02_CODE/           # all relevant source files
  03_DOCS/           # API definitions, design documents, external documentation
```

## Worked Example
**A feature through the whole team.**

1. **Vibe coding for ideation.** The developer explores an unfamiliar third-party API conversationally, getting runnable throwaway code that reveals the shape of the integration. This solves the blank-page problem — and then it is discarded.

2. **Staging the context.** The developer creates `task-context/` and writes `01_BRIEF.md`: the goal, the requirements, the PR description they intend to write, and the style guide. `02_CODE/` gets every relevant source file so the agent sees existing patterns, not just the new module. `03_DOCS/` gets the API definitions discovered in step 1. Note that this is the developer's real work in this model — nothing is retrieved automatically, because black-box retrieval means losing control of what the model sees.

3. **Scaffolder.** "You are a senior software engineer. Based on the requirements in `01_BRIEF.md` and the existing patterns in `02_CODE/`, implement the feature…" The output is a proposal.

4. **Test Engineer.** Given the accepted implementation, writes the full pytest suite covering edge cases per the project's testing philosophy — the tests the developer would have deferred.

5. **Documenter.** Generates markdown API documentation with request/response examples.

6. **Optimizer.** Proposes performance and clarity refactors, each with an explanation of *why* it is an improvement — which is what makes them evaluable rather than stylistic noise.

7. **Process Agent, on commit.** The `pre-commit` hook fires the two-stage review. The critique pass finds 23 items. The reflection pass discards the pedantic ones, prioritizes three real issues, and prints an actionable summary in the terminal — before the commit is finalized.

8. **The developer decides.** Every artifact above is a proposal. The developer validates against domain knowledge and project context, pushes back where the agent is wrong, and iterates in dialogue rather than regenerating from scratch.

## Key Takeaways
1. Vibe coding excels at ideation and prototyping; production work needs a structured human-agent team.
2. Three foundations: human-led orchestration, the primacy of context, and direct frontier-model access.
3. Context is curated by the developer — complete codebase, external knowledge, human brief — never black-box retrieved.
4. Specialist agents are personas invoked by role-specific prompts, not separate applications: Scaffolder, Test Engineer, Documenter, Optimizer, Process Agent.
5. The review agent works in two stages — detailed critique, then reflection that prioritizes and discards low-impact findings.
6. Set up dual frontier providers, a transparent context orchestrator config, a version-controlled prompt library, and Git-hook integration.
7. Agent output is a proposal; the developer is the ultimate quality gate.
8. Refine through iterative dialogue; the reflection output starts a conversation.
9. The relationship is partnership, not contest: developers focus on strategic innovation, resilient architecture, and creative problem-solving.
